# 적용하며 배운 것

agent-colleague 의 단계 0~2(PR #38~#45, 2026-09-24~25), 머지 뒤 리뷰(2026-09-26), c8c-api CCE-4770 에서 리뷰가
실제로 잡아낸 것들이다. 절차는 [migration-stages.md](migration-stages.md) 에 있다.

## 경계 검사

- **denylist 방식이 우회를 만들었다.** 처음 만든 기능 폴더 검사는 denylist 였고, 두 번의 리뷰에서 우회 18건이
  나왔다. `node:os`, `createRequire` 를 거친 `pg`, 템플릿이나 변수로 만든 동적 import, `globalThis['process']`,
  `eval`, `new Function`, `global.process`, `Reflect.get`, `globalThis?.process`, `require.resolve`, `Date.now()`,
  `}` 뒤의 `/` 를 정규식으로 잘못 읽어 코드가 가려진 것 등이다. allowlist 로 바꾸고 18건 모두를 테스트 케이스로
  고정했다.
- **테스트 전용 파일을 통째로 빼면 구멍이 생긴다.** `testing.ts` 를 검사에서 뺐더니, 그 파일을 import 하는 운영
  파일이 `pg` 와 `process` 를 쓸 수 있었다.
- **토크나이저 사본 둘은 따로 어긋난다.** 조립 지점 검사와 기능 폴더 검사가 같은 토크나이저를 각자 사본으로 쓰면
  한쪽만 고쳐진다. 하나로 합치거나 공용 모듈로 옮기면 해결된다. 이 교훈을 여기 적어 두었는데도 main 에는 서로
  어긋나는 사본 둘이 남아 있었다(2026-09-26 리뷰: `}` 뒤 나눗셈 문제가 조립 지점 쪽에만 남아 있었다). 이 파일에
  교훈을 적는 것으로는 부족했다. 같은 PR 에서 코드를 합쳐야 고쳐진다.
- **머지 뒤 리뷰가 우회를 더 찾았다(2026-09-26, origin/main e641ee3).** 테스트 878개 중 877개 통과, 1개 건너뜀,
  실패 0개인 상태에서 아래가 가짜 파일로 통과했다.
  - 조립 지점도 아니고 자기 allowlist 도 없는 모듈(`src/policy` 를 뺀 어디든)이 `host.ts` 의 `gitRun` 과
    `jsonLogger` 를 import 했다. 이 규칙은 `host.ts` 안의 주석에만 있었다.
  - 공용 코드(core, lib)에 `export … from '../session/…'` 파일을 두고 기능 폴더가 그 파일을 import 했다. 기능
    폴더는 언제나 공용 코드를 import 할 수 있지만, 공용 코드 안의 import 는 검사하지 않았다.
  - 옛 위치(`src/tools/`)의 새 연동 파일. 게다가 문서가 tool 을 옛 경로(`session/tools.ts`)에 더하라고 안내하고
    있었다.
  - 기능 폴더에서 `console`, `AbortSignal.timeout`, `performance`, `.mts` 파일이 통과했다. 조립 지점 검사에서는
    `globalThis['process']` 가 통과했다.
- **검사 코드를 합치는 리팩터가 검사를 약하게 만들 수 있다(2026-09-26).** 토크나이저를 공용 파일 하나로 합치자
  새 구멍이 둘 생겼다. 파일 목록을 `isFile()` 로 거르자 심볼릭 링크를 더는 읽지 않았다. `}` 뒤의 `/` 를 나눗셈으로
  읽도록 고치자 정규식 안의 백틱이 그 뒤의 코드를 가리는 구멍이 생겼다. 리뷰어는 **같은 가짜 파일을 옛 테스트와 새
  테스트에 돌려** 옛 테스트만 실패하는 것을 보고 둘을 찾았다. 검사 코드를 바꾸는 PR 은 이 비교를 완료 기준에
  넣어야 한다. 코드를 읽는 방법이 둘인 곳(`}` 뒤의 `/`)은 두 결과를 모두 확인한다.

## 공용 처리 함수

- **헬퍼를 건네는 것만으로는 아무것도 강제되지 않는다.** 기능이 SDK tool 정의를 직접 만들어도 컴파일된다면, 같은
  동작이 두 번 실행되는 것을 막는 실행 기록과 오류 감싸기를 건너뛴다. 기능이 spec 만 돌려주고 공용 코드가 그것을
  감싸도록 바꿨다. 등록할 때 분류와 kind 를 다시 확인하고, 이름이 겹치면 실패한다.
- **쓰기 tool 은 순서를 고정한다.** 실행하고, 기록하고, 응답한다. 이 순서를 테스트로 고정한다.

## 설정과 권한

- **기능에 env 전체를 넘기지 않는다.** 기능이 읽겠다고 선언한 키만 넘기고, 그 선언이 `.env.example` 과 맞는지
  테스트한다.
- **보안 목록(tool 이름과 권한 등급)은 기능 폴더에 두지 않는다. 공용 코드의 목록에 두어, 폴더를 만드는 것만으로는
  붙지 않게 한다.**
- **2026-10-25: 이 지침이 명시적 등록부에서 예약 파일 기반의 찾기로 바뀌었다.** 이 교훈의 권한 부분은 그대로
  유효하다. 찾기는 권한 등급을 주지 않는다.

## 일한 방식

- **단계마다 PR 하나, 동작은 그대로.** 이동 전후의 tool 정의를 스크립트로 뽑아 diff 했다.
- **쌓은 PR 은 문서에서 충돌한다.** 코드보다 `CLAUDE.md` 와 아키텍처 문서의 같은 문단을 여러 PR 이 고친다. 머지
  순서를 정하고, 마지막에 main 과 합친 트리에서 테스트를 다시 돌린다.
- **리뷰 결과는 PR 설명에 옮기기 전에 다시 확인한다.** 한 번은 `grep | head` 로 잘린 출력만 보고 "그런 경우는
  없다" 고 썼다.
- **다음 단계를 막는 것을 먼저 적어 둔다.** 기능 폴더 밖의 코드가 기능의 상수를 import 하는 경우(예: 저장 계약이
  임베딩 차원 상수를 끌어오는 것), tool 이 아닌 경로로 클라이언트를 넘기는 방법, 관리자 전용 tool 을 등록하는
  방법이다.
