# 기존 저장소를 에이전트 친화 구조로 옮기기

기존 저장소를 기능 폴더 구조로 옮기고, 모듈 경계를 실패하는 테스트로 지키게 만들 때 읽는다. 별도 스킬이던
afa(agent-friendly architecture)의 내용을 apply 로 옮긴 것이다. 문서에만 있는 규칙을 lint·아키텍처 테스트로
옮기는 일반 절차는 [enforcement-drafts.md](enforcement-drafts.md) 에 있다. 여기에는 그 문서에 없는 것, 곧 구조를
단계별로 옮기는 절차와 경계 테스트를 쓰는 방법만 둔다. 경계 테스트를 쓰다 실제로 틀렸던 것은
[boundary-test-lessons.md](boundary-test-lessons.md) 에 있다.

기여자(코딩 에이전트와 새로 온 개발자)는 좁은 요청과 가까운 파일 몇 개만 들고 온다. 이 지침은 그 습관을 바꾸려
하지 않는다. 코드와 자동 검사를 고쳐서, 눈앞에서 맞아 보이는 변경이 저장소 전체에도 맞게 만든다. 문서에만 있는
규칙은 끝난 것이 아니다. 어기면 빌드나 테스트가 실패해야 한다.

배경 글(그림 포함): 개념 <https://claude.ai/artifact/SUMYtxfncsjKkvYYeHnria> · agent-colleague 사례
<https://claude.ai/artifact/WvZCW9fExmZqWudHgVctQE> · 머지 뒤 리뷰에서 찾은 우회와 그 수정(PR #46)
<https://claude.ai/artifact/3fuDShZDMKUMUCvRF3Qqwo>

규칙의 출처는 Dune 의 "Agent-friendly architecture" 문서다:
<https://gist.github.com/michaelaflores/5bfed43ea91f89f425be0915c025d2d6>.

이 흐름은 사용자가 구조 이동이나 경계 테스트를 직접 요청했을 때 시작한다. audit 보고서에서 뽑은 항목이 아니므로
apply 본문의 준비 1~4단계와 계획 표를 거치지 않고, 아래 단계 표로 계획을 세워 단계마다 사용자 승인을 받는다.
단계마다 그 단계가 건드릴 파일 목록을 승인 전에 보여 준다. apply 본문의 "보고서 없이 적용하지 않는다", "여러 파일·규칙을
한 번의 승인으로 묶지 않는다" 는 이 흐름에서는 이 단계별 승인과 파일 목록으로 지킨다. 커밋·push·CI 수정은 apply 본문과
같이 승인 없이 하지 않는다.

## 세 가지 방식

요청에서 하나를 고른다. 모호하면 **평가**부터 한다.

| 방식 | 요청 예 | 결과 |
|---|---|---|
| 평가 | "이 저장소 AFA 기준으로 평가해줘" | 규칙마다 `file:line` 근거가 붙은 판정과, 가장 싼 다음 걸음 |
| 계획 | "AFA 이전 계획 세워 줘" | 단계별 PR 목록과 PR 마다 하나씩의 완료 확인 |
| 적용 | "1단계 해 줘", "Jira 를 기능 폴더로 옮겨 줘" | 브랜치, 커밋, PR, 경계 테스트, 고친 문서 |

## 기여자 모델

자기 문맥만 보고 일하는 기여자는 보통 아래처럼 움직인다. 이 행동은 미리 예측할 수 있으므로 설계에 넣는다.

- 가장 가까운 동작하는 패턴을 베낀다.
- 이미 열려 있는 파일을 고친다.
- 컴파일되는 가장 짧은 길을 고른다.
- 호출하는 곳이 보이지 않는 코드는 지우지 않는다.
- 요청받은 구현이 시스템 불변식과 충돌해도 요청대로 한다.

## Dune 의 다섯 규칙

원문 문장 그대로 인용하고, 그 밑에 이 지침이 어떻게 읽고 검사하는지 적는다.

1. > The conventional path requires fewer decisions than a shortcut.

   가장 가까운 코드를 베껴도 올바른 코드가 나와야 한다. 지름길은 정해진 길보다 선택을 더 요구해야 한다.

2. > Forbidden dependencies fail mechanically.

   "A 는 B 를 import 하면 안 된다" 를 테스트나 컴파일러가 실패시킨다. 실패 메시지는 대신 쓸 길을 알려 준다.

3. > Every durable value has one obvious writer.

   DB 테이블, 설정 파일, 저장되는 상태마다 쓰는 모듈이 하나다. 값마다 주인이 달라도 된다. 읽는 쪽은 여럿이어도
   된다.

4. > New product work adds isolated files rather than branches in shared roots.

   새 기능은 새 폴더다. 진입점은 그 폴더 안의 예약된 파일에서 찾아내며, 공용 목록에 등록하지 않는다. 공용 코드에
   기능 이름을 가르는 `if` 를 더하지 않는다.

5. > Exceptions are narrow, explicit, and reviewed as architecture changes.

   아래 "규칙 5 읽는 법" 에서 자세히 다룬다.

패키지 수준에서도 같은 교훈이 적용된다. 공용 프레임워크 코드는 애플리케이션 코드나 기능 코드를 import 하지 않는다.

규칙 밖에서 볼 것이 셋 더 있다.

- **공용 처리 함수.** 빠뜨리면 사고가 나는 단계(실행 기록, 권한 확인, 오류 감싸기)는 공용 함수 안에서 돈다. 기능
  코드는 그 함수를 거치지 않고는 등록할 수 없다.
- **실행·확인 도구.** 코드를 바꾼 사람이 앱을 돌려 결과를 볼 수 있게 하는 고정된 스크립트나 명령.
- **베끼면 안 되는 코드.** 우회 코드, 우회를 설명하는 주석(`workaround`, `hack`, `FIXME`, `임시`. 주석 줄만),
  타입 탈출구, 이전 전 연동. 기여자는 가장 가까운 예시를 베끼므로 하나하나가 퍼진다. 이것은 기존 빚이지 규칙 5 의
  예외가 아니다. 먼저 지금 양을 줄어들기만 하는 예산으로 고정하고(단계 0, 2), PR 마다 줄인다(단계 3, 5).

### 규칙 5 읽는 법

pstack `correct` 의 "Exceptions go on the offending line with a reason, an expiry date, and a human's approval"
을 따르되, 예외 하나의 근거를 한 곳에만 둔다. pstack 의 주석 정리(no-comments)는 정확성을 지키는 lint 를 끄는
주석을 지운다(`comment-sicko` 에이전트 정의). 그래서 예외를 자유 서술 주석으로 쓰지 않는다.

- **좁다**는 파일 하나 또는 심볼 하나다. 디렉터리나 규칙 전체가 아니다.
- **명시적**이라는 것은 예외마다 ID, 이유, 만료일, 승인한 사람이 있다는 뜻이다.
- **단일 출처.** 예외마다 근거는 CODEOWNERS 가 걸린 파일의 allowlist 항목 하나다. 파일 또는 심볼을 키로 두고
  ID, 이유, 만료일, 승인한 사람(작성자가 아닌 사람) 칸을 둔다. import 경계 테스트와 ArchUnit 에서는 검사 코드 옆의
  allowlist 가 그 파일이다. 리뷰에서 같이 보인다.
- **어긴 줄의 표시.** 도구가 읽는 코드 표시가 어긴 줄에 달리는 언어(예: Rust `#[expect(lint, reason = "<allowlist
  ID>")]`)에서는 그 표시에 allowlist ID 만 적는다. 이유·만료일·승인자를 표시에 다시 적지 않는다. 저장소 검사는 두
  방향으로 실패한다. 맞는 allowlist 행이 없는 표시, 그리고 가리키는 표시가 없는 allowlist 행이다. 만료일이 지난 행도
  실패한다.
- **Rust.** `#[expect]` 의 기대가 더는 맞지 않으면 `unfulfilled_lint_expectations` 경고가 나온다. 이것을 실패로
  만들려면 CI 가 경고를 거부해야 한다(`-D warnings` 또는 그 lint 를 deny). `#[expect]` 는 Rust 1.81 에서 안정화된
  것으로 알려져 있다(확인이 필요하다).
- **`@Suppress`·`@SuppressWarnings`.** 이 표시는 allowlist 행과 짝이 맞을 때(파일 또는 심볼과 억제하는 규칙 이름이
  같은 행이 있을 때)만 예외로 센다. 짝이 없으면 예외가 아니라 아래 "베끼면 안 되는 코드" 의 탈출구로 세고, 짝이 있는
  것은 그 개수에서 뺀다.
- **lint 억제 주석.** `eslint-disable…`, `@ts-expect-error`, `# noqa`, `// NOLINT` 는 도구가 읽어도 주석이다.
  pstack 의 주석 정리는 정확성을 지키는 이런 주석을 지운다. TypeScript·JavaScript·Python 에서는 allowlist 만 쓴다.
- **검사가 실패하는 때.** 만료일이 지난 예외가 있을 때, 그리고 더는 아무것도 가리키지 않는 예외가 있을 때다. 실패
  메시지는 어느 예외인지와 "승인을 받아 연장하거나 지운다" 를 알려 준다.
- **만료일이 지나는 날.** 만료된 행이 있으면 코드를 바꾸지 않아도 `verify.sh` 가 어느 push 에서든 실패하고,
  pre-push hook 이 그 push 를 막는다. 이번 변경과 무관한 push 까지 막히지 않도록, 만료 며칠 전부터 곧 만료될 행을
  출력하는 경고를 두기를 권한다.
- **승인.** 작성자가 아닌 사람이 한다. allowlist 파일에 CODEOWNERS(또는 같은 기능)를 걸어 그 사람을 거치게 한다.
  예외를 더하거나 넓히는 변경은 아키텍처 변경으로 리뷰한다.
- **예외가 아닌 것.** 베끼면 안 되는 코드의 기존 양은 지금 상태를 고정하고 줄어들기만 하는 예산이다(단계 0, 2 에서
  고정하고 단계 3, 5 에서 줄인다). 규칙 5 의 예외가 아니므로 만료일을 달지 않는다. 이것은 `correct` 의 "If the
  pattern is already common, fail only when a change adds more" 와 같은 방식이다. 예산을 늘리는 변경은 테스트가
  실패시킨다. 예산을 어디에 두고 어떻게 지키는지는 [enforcement-drafts.md](enforcement-drafts.md) 의 "이미 어긴 곳이
  있을 때" 를 따른다.

## 구성 요소

- **조립 지점(composition root).** 외부 시스템(환경 변수, DB, 네트워크, 메시징, SDK, 프로세스, 타이머)을 만드는
  유일한 파일들. 나머지는 인터페이스를 받는다.
- **공용 코드.** 모든 기능이 쓰는 런타임 코드. 기능 폴더를 import 하지 않는다.
- **기능 폴더.** 외부 서비스나 기능 하나당 폴더 하나(`client`, `config`, 진입점, 테스트). 공용 코드와 자기 폴더만
  import 한다.
- **진입점 찾기(entrypoint discovery).** 조립 지점의 생성기가 기능 폴더 안의 예약된 파일 이름을 훑어, 정적
  import 를 쓰는 타입 있는 색인 파일을 만들어 커밋한다. 색인이 디스크의 폴더와 어긋나면 실패하는 테스트가 있다.
  공용 코드는 찾기에 런타임 동적 import 를 쓰지 않으며, 이 금지에는 예외가 없다. 정적 import 가 컴파일 시점
  검사를 지켜 준다(1단계의 "컴파일되지 않는다"). 프레임워크가 이미 훑는 곳(Spring 컴포넌트 스캔)에서는 색인을
  만들지 않고 찾아낸 집합을 테스트로 고정한다. 권한을 제한하는 시스템에서 진입점을 찾아내는 일이 권한을 주지는
  않는다.
- **권한 분류.** 권한을 제한하는 시스템에서는 진입점마다의 권한 등급이 공용 코드의 한 주인에게 있다. 키는 기능이
  스스로 선언하는 이름이 아니라 진입점 신원(기능 폴더 + 예약 파일)이다. 테스트는 양쪽을 본다. 찾아낸 진입점마다
  등급이 있어야 하고, 등급 항목마다 찾아낸 진입점이 정확히 하나여야 한다(낡은 항목은 실패). 등급 없는 진입점의 실패
  메시지는 "항목을 더해라" 만이 아니라 검토 경로를 알려 준다. 이 목록의 변경은 모두 아키텍처 변경이다. 작성자가
  아닌 사람이 검토하고 승인해야 하며, 그 파일에 CODEOWNERS(또는 같은 기능)를 건다. 이것은 등록 목록이 아니라
  보안 목록이다. 권한을 바꾸는 일이라 검토를 거치는 것이 정상이며, 규칙 4 를 깨지 않는다.
- **경계 테스트.** 위 규칙을 실패하는 테스트로 만든 것. import 와 패키지는 allowlist 로 판정한다. allowlist 가
  불가능한 곳(전역 이름)에서는 denylist 를 쓰고, 그것을 우회할 수 있는 동적 접근은 그 자체를 위반으로 센다.

이 이름들이 스택마다 무엇에 해당하는지는 아래 "스택별 경계 검사" 의 첫 표에 있다. 예시는 agent-colleague(Slack
봇)에서 왔으므로, "tool" 은 그 저장소의 기능 작업 단위(API, 핸들러, 배치 작업)로 읽는다.

## 강제 수준

계획의 "단계" 와 구분하려고 "강제 수준" 이라 부른다. 1이 가장 강하다. 같은 교정이 두 번 나오면(리뷰 코멘트, 또는
사람이 작업 중간에 기여자를 바로잡을 때) 1수준에서 시작해 되는 가장 강한 수준으로 규칙을 옮긴다. 평가와 적용에서는
규칙마다 지금 수준을 적는다. 주석이나 문서에만 있는 규칙(5수준)이 가장 먼저 샌다.

1. 코드 구조: 잘못된 자리가 없다
2. 타입과 컴파일러: 잘못 쓰면 빌드가 실패한다
3. 테스트, lint, CI: 잘못 쓰면 머지되지 않는다
4. 리뷰 봇이나 스킬: 누가 확인할 때 잡힌다
5. 문서와 규칙 파일: 읽고 기억할 때만 지켜진다

## 절차

### 평가

1. 저장소의 `CLAUDE.md`, `AGENTS.md`, 아키텍처 문서를 읽는다. 이미 있는 경계 검사(ArchUnit, import 테스트, lint
   규칙, CI 설정)를 찾는다.
2. 읽기 전용 하위 에이전트에 아래 "평가 질문" 을 주고 평가를 맡긴다. 판정마다 `file:line` 과 쓴 명령을 요구한다.
   빈 grep 결과는 없다는 증거가 아니다. 하위 에이전트는 백그라운드로 띄우지 않는다(apply 본문과 같다).
3. 표 하나로 보고한다. 규칙마다 한 줄이고, **맞지 않음 / 일부 맞음 / 맞음** 에 근거를 붙인다. 점수나 백분율을
   지어내지 않는다.
4. 비용이 가장 낮고 효과가 가장 큰 다음 걸음 하나를 권한다(보통 CI 와 고정 테스트).

### 계획

아래 순서를 기본으로 두고, 저장소에 맞게 단계를 빼거나 합친다. 단계마다 PR 하나 이상이고, 완료 확인이 하나씩
있다. 구조를 옮기는 PR(단계 0~3)은 동작을 바꾸지 않는다. 단계 5처럼 동작을 바꾸는 PR 은 구조 이동과 섞지 않는다.

| 단계 | 내용 | 완료 확인 |
|---|---|---|
| 0 | CI. 조립 지점 경계 테스트(다른 모듈이 조립 지점 파일 자체를 import 하는 것도 막는다). 공용 코드의 import allowlist. 베끼면 안 되는 코드의 고정 테스트(테스트 안의 `파일: 개수` 예산을 소스와 비교하며, 줄어드는 것만 허용). 빠뜨리면 사고가 나는 목록이나 기록(권한 등급, 중복 실행 방지)이 있으면 그것을 고정하는 테스트 | 새 테스트가 CI 에서 돈다. 각각 일부러 깨뜨린 파일에서 실패하는 것을 봤다 |
| 1 | 반복되는 처리를 모으는 공용 처리 함수(`readTool`, `writeTool` 등). 파일은 제자리에 둔다 | 기능 코드가 공용 함수를 거치지 않으면 컴파일되지 않는다 |
| 2 | 시범: 기능 하나를 기능 폴더로 옮긴다. 기능 폴더 경계 테스트, 진입점 찾기(생성기, 커밋된 색인, 색인이 폴더와 맞는지 보는 테스트), **옛 위치 고정 테스트**(옛 위치에 새 파일을 만들면 "기능 폴더를 만들어라" 로 실패)를 더한다. 옛 경로를 가리키는 문서 문장은 같은 PR 에서 고친다 | 이동 전후의 tool·API 정의가 같다(스크립트로 뽑아 diff). 옛 위치의 가짜 파일이 테스트를 실패시킨다. 권한을 제한하는 시스템에서는 권한 등급 없는 가짜 진입점이 빌드를 실패시킨다 |
| 3 | 남은 기능을 PR 하나에 기능 하나씩 옮긴다. 옮길 때마다 옛 위치 목록을 줄인다 | 단계 2 와 같다. 목록이 비면 테스트를 "옛 위치에 파일이 없다" 로 바꾼다 |
| 4 | 실행·확인 도구(이벤트 재생, 로컬 호출 스크립트). 세션마다 새로 쓰는 스크립트가 아니라 저장소나 스킬 폴더에 고정된 명령으로 둔다 | 명령 하나로 앱이 뜨고 증거(응답, 로그, 추적)가 남으며, 그 명령이 `CLAUDE.md` 나 `AGENTS.md` 에 적혀 있다 |
| 5 | 빚 줄이기: 단계 0 에서 고정한 우회·우회 주석·탈출구 예산을 PR 마다 낮춘다. 이전 전 연동 파일은 단계 3 에서 다룬다 | 개수가 줄고, 테스트 안의 예산도 같이 줄었다 |

테스트가 약한 저장소에서는 단계 4 를 단계 2 앞으로 당길 수 있다. 정의 diff 는 같아도 연결이 끊어져 있을 수 있고,
그것은 앱을 돌리거나 통합 테스트를 해야 드러난다.

단계 3 전에 정해 둔다. 진입점이 아닌 경로(알림, 배치 작업, 다른 세션)가 클라이언트를 어떻게 받는지, 관리자 전용
기능의 권한 등급을 어떻게 정하는지, 기능 안의 상수를 기능 폴더 밖의 코드가 import 하고 있으면 그것을 공용 코드로 옮기는
일이다.

### 적용

1. 브랜치를 새로 따고 구현을 하위 에이전트에 맡긴다. 그 단계의 완료 확인과 아래 "경계 테스트 쓰기" 절을 프롬프트에
   그대로 넣는다. 하위 에이전트는 백그라운드로 띄우지 않는다.
2. 경계 테스트는 **일부러 깨뜨린 가짜 파일**에서 실패하는 것을 본 뒤에야 믿는다. 확인한 우회는 모두 테스트
   케이스로 고정한다.
3. 공개 정의(tool 이름, 스키마, API, 순서)를 이동 전후에 스크립트로 뽑아 diff 한다.
4. 읽기 전용 리뷰를 따로 돌린다. 렌즈는 동작이 보존됐는가, 경계 검사에 우회가 있는가, 문서가 코드와 맞는가다.
5. 저장소 `CLAUDE.md`(`AGENTS.md` 가 원본이면 그쪽)의 규칙 문장을 apply 본문 3·4절의 방식으로 정리한다. 강제한
   규칙은 본문을 지우고 "→ <규칙 이름·테스트 경로>" 한 줄로 줄인다. 강제할 수 없는 규칙(C)은 해당 모듈 문서의 "강제할
   수 없는 규칙" 절이나 `docs/ANTIPATTERNS.md` 에 이유와 함께 옮긴다. `강제 불가: <이유>` 는 ANTIPATTERNS 항목
   형식에서만 쓰는 표기다. 예외 allowlist 가 바뀌면 테스트와 문서를 같이 바꾼다.

## 경계 테스트 쓰기

- **import 와 패키지는 allowlist 로 판정한다.** agent-colleague 의 denylist 판은 두 번의 리뷰에서 우회 18건을 통과시켰다.
- **기능 폴더 경계가 기대는 것을 검사한다.** 기능 폴더가 공용 코드를 자유롭게 import 해도 되면, 공용 코드의
  import 도 allowlist 로 검사한다. 그렇지 않으면 공용 코드의 재export 파일 하나로 경계를 넘는다.
- **다른 모듈이 조립 지점 파일을 import 하는 것을 막는다.** 외부 패키지 이름만 보면 조립 지점이 감싸 둔 함수(프로세스
  실행기, 로거)를 빌려 쓰는 코드가 통과한다.
- **검사하는 확장자 밖의 소스 파일은 위반으로 센다.** `.ts` 만 읽는 검사는 `.mts` 나 `.js` 로 우회된다.
- **예외는 위 "규칙 5 읽는 법" 을 따른다.** 파일이나 심볼 하나, 이유·만료일·승인자, 만료됐거나 아무것도 가리키지 않는
  예외는 테스트 실패다. 베끼면 안 되는 코드의 기존 양은 예외가 아니라 줄어드는 예산으로 따로 둔다.
- 검사가 읽지 못하는 코드(동적 import, 문자열로 만든 경로, `globalThis`·`eval`·리플렉션 같은 전역 객체 접근)는 그
  자체를 위반으로 센다.
- 검사의 알려진 사각지대를 테스트 파일 맨 위에 적는다.
- 테스트 전용 파일(`testing.*`, 픽스처)을 통째로 검사에서 빼지 않는다. 운영 코드가 그 파일을 import 하는 것을 막는다.

## 하지 않는 것

- 동작 변경과 구조 이동을 한 PR 에 섞지 않는다.
- 진입점을 찾아내는 일이 권한을 주게 하지 않는다. 찾아낸 진입점의 권한 등급은 그 목록의 단 하나뿐인 주인이 정한다.
  기능이 스스로 등급을 고르지 않고, 그 목록의 변경은 작성자가 아닌 사람의 검토와 승인이 필요하다. Spring 컴포넌트
  스캔처럼 프레임워크가 자동 등록하는 곳에서는 등록된 빈의 집합을 테스트로 고정하고, 권한 등급이 없는 빈이 있으면
  실패시킨다.
- 기능 폴더에 환경 변수 전체나 외부 클라이언트 전체를 넘기지 않는다. 기능이 선언한 키와 인터페이스만 넘긴다.
- 직접 잰 효과만 보고한다.
- 불편하다는 이유만으로 검사를 느슨하게 하지 않는다. 검사가 굽어야 하면 규칙 5 에 따라 좁고 명시적인 예외(이유,
  만료일, 승인자)를 더하고 아키텍처 변경으로 리뷰한다.
- 새 방식을 더하고 옛 방식을 남겨 두지 않는다. 이동이 끝날 때까지 옛 목록을 테스트로 고정하고, 옛 경로를 가리키는
  문서를 고친다.

## 평가 질문

판정마다 `file:line` 과 확인에 쓴 명령을 적는다. 확인하지 못한 항목은 "확인 필요" 로 적는다.

### ① 정해진 길이 가장 쉬운가

- 기능 하나(tool, API, 외부 연동)를 더하려면 공용 파일을 몇 개 고쳐야 하는가? 최근의 실제 커밋 하나를 골라
  `git show --stat` 으로 센다.
- 새 기능이 베끼게 될 "가장 가까운 예시" 가 올바른 패턴인가, 예외적인 코드인가?
- 분류(읽기, 쓰기, 관리자, 권한 등급)를 빠뜨리면 컴파일이 실패하는가?

### ② 금지된 의존이 자동으로 실패하는가

- 조립 지점 밖의 코드가 환경 변수, DB, 네트워크, 타이머, 프로세스를 여는 것을 무엇이 막는가? (테스트 파일 이름을
  적는다.)
- 계층·모듈 사이의 금지된 import 를 무엇이 막는가? (ArchUnit, import 테스트, lint 규칙.)
- 그 검사가 CI 에서 도는가? CI 설정 파일 경로를 적는다.
- 검사가 allowlist 인가 denylist 인가? denylist 면 동적 import, 리플렉션, 전역 객체가 우회하는지 가짜 파일로
  확인한다.

### ③ 모든 영속 값에 주인이 하나인가

- DB 테이블, 설정 파일, 저장되는 상태마다 쓰는 주인이 분명한가? 값마다 주인 모듈 밖의 쓰기(주인 밖의 SQL 이나 ORM
  쓰기)를 grep 한다.
- 주인 모듈의 계약을 실제 DB 로 돌리는 테스트가 있는가?

### ④ 새 작업이 새 파일을 더하는가

- 기능마다 코드가 파일 하나에 있는가? 줄 수와 기능 수를 센다.
- 공용 파일에 기능 이름으로 가르는 `if`, `when`, `switch` 가 있는가?
- 진입점이 기능 폴더 안의 예약된 파일에서 찾아지는가, 기능을 더하려면 공용 목록을 고쳐야 하는가? 찾기가 정적 import 를
  쓰는 생성된 커밋 색인(과 색인이 폴더와 맞는지 보는 테스트)인가, 공용 코드의 런타임 동적 import 인가?
- 권한을 제한하는 시스템이면 권한 분류가 기능 폴더 밖의 한 주인에게 있는가? 기능이 선언하는 이름이 아니라 진입점
  신원(기능 폴더 + 예약 파일)을 키로 쓰는가?
- 테스트가 양쪽을 보는가? 찾아낸 진입점마다 등급이 있고, 등급 항목마다 찾아낸 진입점이 정확히 하나다(낡은 항목은
  실패). 등급 없는 진입점의 실패 메시지가 "항목을 더해라" 만이 아니라 검토 경로를 알려 주는가?
- 권한 분류 목록의 변경을 작성자가 아닌 사람이 검토하고 승인하는가(그 파일의 CODEOWNERS 또는 같은 기능)? 이 목록은
  등록 목록이 아니라 보안 목록이다.

### ⑤ 예외가 좁고, 명시적이고, 검토되는가

- 예외마다 파일 하나 또는 심볼 하나로 범위가 좁혀져 있는가? 디렉터리나 규칙 전체로 넓지 않은가?
- 예외에 ID, 이유, 만료일, 승인한 사람이 있는가? CODEOWNERS 가 걸린 allowlist 행에 있는가, 자유 서술 주석이나
  문서에만 있는가? 어긴 줄에 도구가 읽는 표시가 있으면 allowlist ID 만 담고 allowlist 행과 서로 맞는가?
- 만료일이 지난 예외, 그리고 더는 아무것도 가리키지 않는 예외(표시 없는 allowlist 행, allowlist 행 없는 표시)가
  테스트를 실패시키는가?
- 예외를 더하거나 넓히는 변경을 작성자가 아닌 사람이 아키텍처 변경으로 리뷰하는가(예외 목록이나 검사 파일의
  CODEOWNERS)?

### 셋 더

- **공용 처리 함수:** 기능 코드가 실행 기록, 권한 확인, 오류 감싸기를 건너뛸 수 있는가? 건너뛴 코드가 그래도
  컴파일되는가?
- **실행·확인 도구:** 고친 뒤 에이전트가 앱을 직접 돌릴 수 있는 명령이 있는가? 문서 어디에 적혀 있는가?
- **베끼면 안 되는 코드:**
  - 우회를 설명하는 주석을 주석 줄로 좁혀 센다(예: `grep -rniE '//.*(임시|workaround|hack|FIXME)'`). `임시` 는
    도메인 단어에도 걸리니(임시 비밀번호, 임시저장) 걸린 줄을 읽고 걸러 낸다. Kotlin 의 `TODO()` 는 함수 호출이라
    따로 확인한다.
  - 타입 탈출구를 센다. TypeScript: `:\s*any\b|as any\b`, `as never`, `as unknown as`, `@ts-ignore`. Kotlin:
    `@Suppress\(` 와 검사 없는 `as` 캐스트. Java: `@SuppressWarnings`. allowlist 행과 짝이 맞는 `@Suppress`·
    `@SuppressWarnings` 는 규칙 5 의 예외이므로 센 개수에서 뺀다. Kotlin 의 `!!` 는 흔한 문법이므로 참고용
    개수로만 둔다.
  - 먼저 그 grep 이 걸려야 할 낱말 하나로 동작하는지 확인한다. 결과는 `file:line` 으로 적는다.
  - 같은 일을 하는 방식이 둘 이상 공존하는가? (예: 기능 폴더로 옮긴 연동과 옛 위치에 남은 연동.) 새로 온 사람이
    어느 쪽을 가장 가까운 예시로 보겠는가?
  - 옛 방식을 가리키는 문서가 있는가? `file:line` 을 적는다.
  - 양이 늘어나는 것을 막는 검사(목록을 고정하는 테스트나 lint 규칙)가 있는가? 지금 양을 줄어들기만 하는 예산으로
    고정하는 것은 괜찮다. 이것은 기존 빚이며 예외가 아니다.

## 스택별 경계 검사

### 구성 요소 지도

| | TypeScript / Node | Kotlin / Spring | Python |
|---|---|---|---|
| 조립 지점 | 프로세스를 시작하는 파일(`main.ts` 등) | `@SpringBootApplication` 클래스와 `@Configuration` 모듈(외부 클라이언트 빈을 만드는 곳) | `main.py`, 앱 팩토리(`create_app`), DI 컨테이너 설정 |
| 기능 폴더 | `src/<feature>/` | 기능 패키지 `…/<feature>/`(컨트롤러, 서비스, 클라이언트를 함께) 또는 Gradle 모듈 | 패키지 `app/<feature>/` |
| 진입점 찾기 | 기능 폴더 안의 예약 파일 이름(가정한 예: `src/<feature>/entry.ts`). 조립 지점의 생성기가 그것을 훑어 정적 import 를 쓰는 타입 있는 색인 파일을 만들어 커밋한다. 색인이 디스크의 폴더와 어긋나면 테스트가 실패한다. 공용 코드에 런타임 동적 import 는 없다 | 컴포넌트 스캔 안의 기능 패키지. 찾아낸 빈의 집합을 기능 폴더에 맞춰 고정하고 등급 없는 빈이 있으면 실패하는 테스트 | 예약 모듈이 있는 패키지(가정). 생성기가 일반 import 를 쓰는 색인 모듈을 만들어 커밋하고, 색인이 디스크의 패키지와 어긋나면 테스트가 실패한다 |
| 경계 검사 도구 | 토크나이저나 AST 테스트, dependency-cruiser, eslint `no-restricted-imports`·`no-restricted-globals` | ArchUnit (+ Konsist) | import-linter(계약), 필요하면 AST 검사 테스트 |
| 외부 연결 인터페이스 | `ports.ts` 의 인터페이스 | 도메인 모듈의 인터페이스 + 어댑터 빈 | `Protocol` 또는 ABC |

옛 방식은 명시적 등록부였다. 기능을 나열하는 `index.ts`, 컴포넌트 스캔 밖의 빈을 `@Import(...)` 로 이름 붙이는 등록
모듈, 라우터와 핸들러를 나열하는 모듈(`include_router` 목록 같은 것)이 그렇다. 명시적 목록은 찾기를 안전하게 만들 수
없을 때의 대안이다. 표의 `entry.ts` 와 Python 찾기 예시는 가정이다. PR #46 시점에 agent-colleague main 은 여전히
명시적 `capabilities/index.ts` 목록을 썼다.

도구별 lint·금지 API 설정 예시와, 이미 어긴 곳이 있을 때 기준 파일(baseline)을 다루는 방법은
[enforcement-drafts.md](enforcement-drafts.md) 의 "이미 어긴 곳이 있을 때" 가 정한다. 아래에는 그 문서에 없는 것만
적는다.

### TypeScript (agent-colleague)

main 에 있는 것(2026-09-25, PR #38, #45):

- `src/core/boundaries.test.ts`: 조립 지점(`src/main.ts`, `src/host.ts`) 밖의 코드가 외부 패키지, 타이머, 전역
  fetch 를 쓰면 실패한다. `파일: 개수` 꼴의 `TIMER_EXCEPTIONS` 목록(과 같은 꼴의 다른 예외 목록)은 2026-09-25
  agent-colleague main 의 스냅샷이다. 규칙 5 에 못 미친다. 심볼 대신 개수를 쓰고 이유가 없다. 바꾸려면 파일 또는
  심볼 하나당 항목 하나에 ID·이유·만료일·승인자를 단다. 실제로는 빚인 항목은 줄어드는 빚 예산으로 옮긴다.
- `src/capabilities/capabilities.test.ts`: 기능 폴더 경계.
  - import 는 `src/core`, `src/lib`, 그 기능 자신의 폴더로 제한한다. 패키지는 allowlist 를 쓴다(`zod`. SDK 는
    `import type` 만).
  - `FORBIDDEN` 표: `process`, 타이머, 전역 `fetch`, `globalThis` 와 `global`, `eval`, `Function`, `Reflect`,
    `.constructor`, `require` 와 `createRequire`, `Date.now` 와 `new Date`.
  - 경로가 문자열 리터럴이 아닌 `import(` 는 위반이다.
  - 운영 파일이 `testing.ts` 나 `*.test.ts` 를 import 하면 위반이다.
- `src/core/capability.ts`: 기능은 tool 정의가 아니라 spec(`{ kind: 'read' | 'write', name, description, shape,
  run }`)을 돌려주고, 세션이 그것을 공용 처리 함수로 감싼다. tool 이름 분류(`TOOL_CLASS`)와 kind 가 어긋나면
  컴파일되지 않는다.

이 지침이 권하는 찾기 설계(지금 main 이 하는 것은 아니다):

- 조립 지점의 생성기가 기능 폴더 안의 예약 파일을 훑어 타입 있는 색인 파일을 만들어 커밋한다. 색인은 정적 import 를
  쓴다.
- 색인이 디스크의 폴더와 어긋나면 실패하는 테스트가 있다. 양쪽을 본다. 색인에 빠진 폴더, 그리고 폴더 없는 색인
  항목이다.
- 정적 import 가 컴파일 시점 검사를 지킨다. `TOOL_CLASS` 와 kind 가 어긋나면 여전히 컴파일되지 않는다. 런타임 동적
  import 는 이 검사를 잃는다.
- 경로가 리터럴이 아닌 `import(` 금지는 조건 없이 유지한다. 찾기에도 예외를 주지 않는다.
- `TOOL_CLASS` 의 키는 기능이 선언하는 이름이 아니라 진입점 신원(기능 폴더 + 예약 파일)으로 한다. 아래 "공통" 의
  권한 분류를 본다.

만드는 법:

- TypeScript 7 에는 안정된 파서 API 가 없다. 그래서 주석, 문자열, 템플릿, 정규식 리터럴만 가르는 작은 토크나이저로
  코드를 읽는다. 파서가 있는 환경에서는 AST 를 쓰는 편이 더 정확하다.
- 이 방식은 텍스트만 본다. `obj[name]` 같은 계산된 속성이나 `const D = Date; new D()` 처럼 다른 이름으로 접근하는
  것은 잡지 못한다. 이 한계를 파일 맨 위에 적는다.
- dependency-cruiser, eslint `no-restricted-imports`, `import/no-restricted-paths` 로도 import 경계를 만들 수 있다.
  전역 사용 금지(`process`, `Date`)에는 lint 규칙(`no-restricted-globals`, `no-restricted-syntax`)을 더한다.

### Kotlin / Spring (c8c-api)

c8c-api CCE-4770 에서 한 것(Bitbucket PR #385, 2026-10-01 머지, c8c-api 커밋 990fc1b7a4):

- ArchUnit 규칙은 `test-module` 의 `DependencyCheckUtil` 에 있고, 앱 모듈마다 테스트 클래스에서 그것을 부른다.
- 예외는 검사 옆에 `setOf(...)` 로 이름을 나열한 allowlist 와 이유로 두었다. 만료일과 승인자 칸은 없다.

규칙 5 를 채우려면 더할 것:

- allowlist 항목마다 ID, 만료일, 승인한 사람 칸을 더하고, 파일 또는 클래스 하나 단위로 쓴다. 만료됐거나 아무것도
  가리키지 않는 항목은 테스트가 실패하게 하고, allowlist 가 있는 파일에 CODEOWNERS 를 건다.
- 베끼면 안 되는 코드(우회 주석, 짝 없는 `@Suppress`, 검사 없는 캐스트)의 개수를 고정할 때는 테스트 코드 안에
  `파일: 개수` 목록을 쓰고 소스의 개수와 비교한다. 이 예산은 규칙 5 의 예외가 아니라 줄어드는 기존 빚이다. 기존
  위반 기준 파일을 다루는 정책은 [enforcement-drafts.md](enforcement-drafts.md) 를 따른다.
- 메서드 수준 규칙(예: Redis 호출 지점은 fallback 을 거친다)은 Kotlin 컴파일러가 만드는 합성 메서드를 따라가야
  한다. 람다 `$lambda$N`, suspend 람다의 `enclosingCodeUnit`, private 헬퍼가 그렇다.
- 기본으로 `JavaClasses` 를 `by lazy` 로 한 번만 import 해서 규칙들이 공유한다. (메서드 수준 fallback 규칙은 범위가
  달라 따로 import 한다.) CCE-4770 작업 중 잰 값: 새 규칙 묶음이 app 은 19.3초에서 4.8초로, admin 은 16.2초에서
  4.5초로 줄었다.

### Python

- import-linter 의 `layers`, `forbidden`, `independence` 계약으로 계층 방향과 기능 패키지 사이의 import 금지를 CI
  에서 강제한다.
- 전역 사용 금지(`os.environ`, `time.time`, `requests` 직접 호출 등)는 import-linter 가 잡지 못한다. 기능 패키지를
  `ast` 로 읽어 이름을 찾는 테스트를 따로 둔다.
- Jenkins 가 이 테스트를 돌리는지 따로 확인한다. 로컬에서만 돌면 원칙 ②(금지된 의존이 자동으로 실패한다)를 채우지 못한
  것이다.

### 공통

- 검사를 만든 뒤에는 **일부러 규칙을 깨는 가짜 파일**로 실패하는지 확인한다. 실패 메시지가 대신 쓸 길을 알려 줘야
  한다.
- CI 에서 돌지 않는 검사는 강제 수준 4 와 효과가 같다.
- 권한 분류(권한을 제한하는 시스템):
  - 공용 코드의 한 주인이 목록을 갖는다. 키는 기능이 선언하는 이름이 아니라 진입점 신원(기능 폴더 + 예약 파일)이다.
  - 테스트는 양쪽을 본다. 찾아낸 진입점마다 등급이 있고, 등급 항목마다 찾아낸 진입점이 정확히 하나다. 낡은 항목은
    실패한다.
  - 등급 없는 진입점의 실패 메시지는 "항목을 더해라" 만이 아니라 검토 경로(작성자가 아닌 사람이 목록 변경을 검토하고
    승인한다)를 알려 준다.
  - 목록의 모든 변경은 아키텍처 변경이다. 그 파일에 CODEOWNERS 또는 같은 기능을 건다.
